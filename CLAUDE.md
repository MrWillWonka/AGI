# The Path to AGI

Browser-based incremental (idle/clicker) game. Vanilla JS, no build step, no runtime dependencies.

## Commands

```bash
python3 server.py            # http://localhost:8000, no-cache; add --no-browser in headless envs, or pass a port
node --test                  # engine unit tests (Node 18+, no install needed)
```

Open `/?debug` (or press <kbd>`</kbd>) for the debug panel: add resources/attributes, rate multipliers, simulate time, unlock everything, live state view.

## Layout

| File | Role |
|---|---|
| `engine.js` | **All game rules and data**, no DOM. UMD: `window.AGIEngine` in the browser, `require()` in Node |
| `training-path.js` | Training Path physics: trail geometry and a fixed-step ball sim (`window.TrainingPath` / `require()`). Pure: no DOM, no clock, no randomness |
| `game.js` | `window.AGI`: builds the UI from engine data, input (hold-to-repeat), 100 ms loop, render, save/load/export, and the Training Path canvas view |
| `debug-panel.js` | Dev tools; talks only to `AGI.debug` |
| `index.html` | Static shell; dynamic parts are generated by `game.js`, values bound via `data-bind="key"` (see `bindValue`) |
| `styles.css` | All styles. "Night survey" single dark theme: tokens on `:root`, fonts Chakra Petch (display), Atkinson Hyperlegible (body), JetBrains Mono (numbers). Screen-size tiers at the end |
| `tests/*.test.js` | `node:test` suites for the engine and the Training Path |

## Architecture rules

- **Content is data.** Actions, tabs, upgrades, milestones, achievements and phases are arrays in `engine.js`. Add an upgrade by adding an `UPGRADES` entry (`scale` = repeatable, `max: 1` = one-time, `grants` = attributes per level, `requires`/`unlock`/`hint` = gating) and, if it affects production, a term in `derive()`. The UI picks it up automatically.
- **Derive, don't store.** Production rates come from `derive(state)` using upgrade levels; phase comes from `phaseIndex(state)` using attributes. Only store what the player earned (resources, attributes, levels, unlocks, achievements, stats).
- **Unlocks are sticky.** `evaluate()` records milestone/upgrade unlocks in `state.unlocked` and achievements in `state.achievements`; it returns what changed so `game.js` can log/toast it once.
- **Saves.** `localStorage['agiGame']`, versioned (`SAVE_VERSION`). `migrate()` sanitizes any input (wrong types, negatives, unknown ids) and converts the original v1 format. If you change the state shape, bump `SAVE_VERSION`, extend `migrate()`, and add a test.
- **Automation converts, it never creates.** The Auto-Collector spends CP for DP and the Research Assistant spends CP and DP for RP, at the manual action prices. It may only use the **automation budget** (`settings.autoBudget`, 0–100% of each second's CP and DP production, default 50%, slider in the lab) and never touches the stockpile, so compute never falls. Over budget, both slow down evenly (`derive().autoThrottled`). Only hardware creates CP. The top-bar rates are net (`cpNet`, `dpNet`).
- **Lab pacing ties into training:** the Auto Data Collector unlocks after the 3rd skill (Image Recognition) and the Research Assistant after the 5th (Language Modeling), so automation is a reward for going back to the trail. Bot timings: Auto Data Collector ≈ 22 min, Research Assistant ≈ 34 min. Basic CPU and Server Cluster costs scale ×1.18 per level.
- **Offline progress** is applied on load and for long gaps between ticks, capped at `MAX_OFFLINE_SECONDS`, and respects `settings.offline`.
- Keep `engine.js` free of DOM/`window` so it stays testable.
- **Training Path** (how the AI learns):
  - The trail is a series of stretches. Stretch k runs from a checkpoint to **skill hill k** (fixed, grows each stretch). Cresting it learns `skillAt(k)`: attributes plus a permanent bonus summed in `derive()` via `skillBonuses()`.
  - Each **roll** starts at the checkpoint over **random rolling hills** (`rollingHills(k, seed)`, new seed per roll from `rollSeed`). The roll ends when the ball rests with no pushes left, or crests the skill hill. Distance earns **XP** (`finishRoll`), and the furthest roll is the stretch record (`path.best`).
  - Once the ball lacks the energy to clear either neighbouring hill it is "trapped" and gets heavy damping, so it settles in about a second instead of sloshing. Full momentum otherwise.
  - Pushes add a fixed amount of *energy* (pushing against a backward roll is wasted), and drag is partly quadratic. So saving pushes to rescue a stalling ball beats firing them early. Tests guard this; keep it true when tuning.
  - **Pushing is hold-to-charge.** A meter sweeps up and down while the button (or Space/Enter, or the canvas) is held, and release fires at that fraction of `pushPower`.
    - Every push costs CP and DP by `pushCost(s, charge)` (∝ charge², scaled per stretch), so passive income gates how hard you can push. The meter only reaches `affordableCharge()`.
    - Each push has a **bonus zone** (`bonusZone(seed, index, width, perfect)`, centred between 50% and 85%), and `zoneHit()` classifies a release as `'clean'`, `'perfect'` or none.
    - A clean push banks a small flat amount of XP at once (`grantPushBonus`) and adds `cleanRollBonus` to the roll's distance XP; a perfect push counts as `perfectMult` clean pushes (`cleanUnits`). This is the trade-off: steady XP from the zone, or full charge for distance.
    - Sweet-spot upgrades: Hyperparameter Search and Automated Tuning (width), Benchmark and Leaderboard Prizes (flat XP), Curated and Hand-Labelled Data (run bonus), Perfect and Fine Calibration (adds and widens the perfect spot). GPU nodes also slow the sweep (`sweepScale`; the base sweep is `CHARGE_SWEEP_MS` 1250). The Auto-Trainer pushes at its full budget and never scores clean pushes.
    - XP follows the ball: the live pill shows `rollXp` at the ball's *current* position, and the payout uses where it stops (rolling back loses XP). The result card sits top-right, clear of the checkpoint; launching fades it.
  - Slope friction (`SLOPE_DRAG`): steeper slopes sap more speed than gentle ones.
  - **Friction stays a skill.** Upgrades only take the edge off: each drag step is −5% (`friction`), and "less steep hills" (`slope` stat → `hillScale`, ×0.94 per step) really lowers the *rolling* hills, never the skill hills (`rollingHills(k, seed, hillScale)`). Skills add little glide. Don't make hills trivial.
  - **Difficulty grows every stretch:** `skillHeight` ×1.5 per stretch, and `stretchLength` = 10·1.25^k + 4k (10, 17, 24, 32 … 92 by stretch 8), so each skill hill is clearly further away than the last (`training-path.js`). Later stretches pay more (`xpScale` 1.5). Skills answer with growing bonuses (push %, extra pushes, a little glide; `SKILLS` and frontier skills), and the tree's outer ring (Quantum Accelerator, Exascale Cluster, Superconductors, Neural Compression, IPO) is priced for the late hills.
  - **Cleared stretches train themselves:** each learned stretch earns `stretchXpAt(k) × PATH.clearedRate` (1/600) XP per second (`derive().xpPerSec`, applied in `tick()`, shown on the XP chip). It's slow on purpose.
  - **Drama** (`game.js`):
    - A *nail-biter* (`nailBiter()`) is the ball climbing near the top of a big hill with about as much energy as it needs. It brings slow motion (`path.timeScale`), a camera push-in raised to the ball (`cameraTarget` with `cam.bottom`), a vignette and "Will it learn <skill>?" (or "Come on…" on a rolling hill).
    - Rolls use `rollOut`: cresting the skill hill fires `celebrateSummit()` (a SUMMIT! banner, confetti across the whole trail, slow motion, the push-in held). The ball then rolls down the far side, and the skill is announced when that roll ends (an `end` event with `crested: true`).
    - Slow motion only applies on screen; background runs keep real time.
  - **Hill floor:** a run pays at least `PATH.hillFloor` × hills crossed (`hillsBefore(maxX)`, passed to `rollXp`/`finishRoll` as `hills`), so short runs still earn something.
  - **Runs and the dev screen.** One run is one roll over a long stretch (about 10–12 rolling hills before the skill hill). When it ends, the result card waits (`path.done`) with **Run again** (or hold the push button) and **Upgrades →**, which switches the bay from `#runView` to `#devView`: where you stand, XP to spend, the skill tree and Start run. Nothing advances on a timer, except with the Auto-Trainer, which starts the next roll by itself. `path.view` is `'run'` or `'dev'`, and physics only runs in `'run'`. The first visit goes straight to the run view; later visits open the dev screen.
  - **Skill tree.** Training upgrades (`tab: 'training'`) are nodes with a `tree: {x, y}` grid position around the Training Core at (0, 0), an `icon` (glyphs in `ICONS` in `game.js`), `requires` (the adjacent node they grow from; none means attached to the core) and a `boost` per level, summed by stat in `treeBoosts()` and applied in `derive()`. Branches: Power (up), Precision (right), Recursion (down), Capability (left), listed in `TREE_BRANCHES`. A node becomes buyable when its parent is owned (`evaluate()` unlocks `up:<id>`). Tests check that nodes don't overlap and are adjacent to their parent.
    - **The seed:** everything grows from **Initial Weights** at the centre (0, 0), 1 XP and one level (+5% sprint strength). It is drawn as the core's diamond (`.tree-node.seed`).
    - **Sparse by design:** every node has 1–3 levels. The ring around the seed costs 4–8 XP with 1–2 levels, the next ring has some one-level nodes, and 3-level nodes only start further out. Each node costs more than its parent. The roots are the basics, so early progression is sprint strength (GPU Cluster), one or two more sprints and less wait (Investor Funding → Faster Chips), and better XP (Bigger Datasets, `xp` stat → `xpMult`). Mechanics such as the sweet spot, the view ahead and automation come after. More strength comes from tiers further out (GPU Cluster → Bigger GPU Cluster → GPU Supercluster), not from stacking levels. The UI shows only nodes you can buy and, as red locks, the next step past them; the rest stay hidden and the tree's bounds grow as it opens (`treeBounds`). A first return buys about one node. Tests enforce the shape.
    - **Mystery:** a locked node shows only a lock. Its detail reads "???" and "Unknown research", and names only what it grows from. **Secret nodes** (`secret: true`: Batch Normalization, Data Augmentation, Warm Restarts) never show, not even as a lock, until their parent is owned. Add more secrets to reward exploring.
    - The tree must not get `will-change: transform`: the browser would cache it as a bitmap at 1× and blur it when zoomed.
    - The tree sits in `#treeViewport`, a camera you can drag (pan), wheel or pinch (zoom about the pointer) and control with +/−/reset buttons; double-click empty space resets it (`treeCam`, `zoomTreeAt`). A drag of 5 px or more swallows the click, so dragging across a node never selects it.
  - The node-detail panel is rebuilt only when its node, state or level changes: `render()` runs every tick, and replacing the button mid-click swallows the click.
    - To add a node: an `UPGRADES` entry with `tab: 'training'`, a free grid cell next to its parent, an icon and a `boost` (stats in `TREE_STATS`).
  - Progression is bought with XP in the skill tree. GPU Cluster adds strength, Faster Chips cuts the wait, and Investor Funding adds training sprints per run (the base is 1, the launch only). The Auto-Trainer appears after a Transcend.
  - Push strength comes from upgrades, skills and `sqrt(globalMultiplier)`. **Never tie it to Intelligence**: skills grant Intelligence, so the loop runs away (tested).
  - The engine owns the economy (`PATH`, `rollCost`, `payRoll`, `rollXp`, `finishRoll`, `learnSkill`); `training-path.js` owns the physics; `game.js` runs rolls, follows the ball with the camera and draws the trail.
  - Only `path.learned`, `path.best`, `res.xp` and `stats.rolls` are saved; an interrupted roll is simply lost.
  - Simulates while the page is open, never offline. Off screen (in the rack, the lab or the facility), a run in flight still finishes and the Auto-Trainer keeps starting new ones (`runsInBackground`); otherwise the loop sleeps.
  - **Lanes:** the Training Cluster's first three blade columns are a `canvas.lane` (`drawLanes`, every run-loop frame, on a 50 ms timer while the rack or facility is on screen, and after each camera refresh), in the rack and in its facility camera copy. Before the Auto-Trainer it is a monitor that **only shows what runs have seen**: the stretch up to the furthest point reached (the record, or the run in progress), scaled to what's known, with a dotted floor and `?` beyond (NO DATA before the first run). The seen part is dimmed, with a scan sweeping it every `LANE_SCAN_SECONDS` with a fading trail and a bright head on the line, and the best run marked (static under reduced motion). With the Auto-Trainer it goes live and follows the ball. Each cleared stretch adds a two-column lane (newest first, up to `MAX_CLEARED_LANES`) where a ball crawls along that stretch: the section automating itself (`buildTrainingArt`). `runLanes()` is 1 for now; concurrent runs will add lanes, each drawing its own ball.
  - Planned (design doc): opposing forces as special terrain that pushes the ball back, and prestige buffs along the trail. Add them as terrain data, like rolling hills.
  - Planned (much later in the tree): **launching off the line**, a jump that clears several hills at once, and **clearing more than one skill hill in a run** once the player is overpowered (the trail would continue into the next stretch after the roll-out). Gate both deep in the late game. The late tree also needs more to buy: the balance bot ends with lots of unspent XP.
  - **Text style everywhere:** skills (`SKILLS`, plus `FRONTIER_QUIPS` for generated ones) and every upgrade have a `flavor` too. It shows in italics on lab cards (as a `#` comment in the software terminal), on the Skill learned card and in the log.
  - **Node text:** every training node has a `flavor` (a one-line quip, ≤ 70 characters: straightforward, quippy or funny, e.g. Investor Funding: "Dad lent you $100. Don't tell Mum.") and an `effect` (the plain bonus, ≤ 80 characters, e.g. "+1 training sprint per run"). The node detail shows both. Tested.
  - **Framing:** the player is an AI research team pushing a model to its limits. Pushes are **training sprints** in everything the player reads (code keeps `push`/`pushes`). Upgrade names are AI-lab terms (Better Optimizer, Smoother Loss Landscape, Hyperparameter Search, Bigger Datasets, Eval Dashboards…) with plain effect text ("Training keeps its momentum longer").
  - The ball is drawn centred on the line, riding it like a bead on a wire.

## Screen layout

Everything grows as it unlocks, and locked things never say what they are: a sealed placeholder (`???`) hints that more is coming. Keep it that way when adding content.

- **Top bar:** resource and attribute chips (`data-show="<unlock key>"` hides a chip until it matters), the phase bar and the Journal button.
- **Facility** (`#facility`, the zoomed-out floor plan): one tile per room in `ROOMS` (`game.js`): Lab, Server room, R&D, then Boardroom, Signals room and Mirror room (phases 1–3, not built yet). Unlocked rooms show live status. The next `SEALED_ROOMS` (2) locked rooms show as anonymous "Sealed wing" tiles, and the rest aren't drawn, so the plan grows. Clicking a tile zooms into the room (`zoomIn`/`zoomOut`, Web Animations API). The facility and rooms share one grid cell in `.stage` so both are on screen during a zoom. Each room's "← Facility" button zooms out and pulses while a newly opened room is unvisited (`localStorage['agiRoomsSeen']`). The current view is kept in `localStorage['agiRoom']`. A new room is a `ROOMS` entry plus a `.room[data-room=id]` section.
- **Facility cameras:** each open room in `CAMERAS` (`game.js`) has a live feed on its tile: a scaled-down, inert copy of the room (`snapshot()` strips ids and `data-facility`/`data-bind`/`data-next`, and drops the `room` class and the room bar). It refreshes every second while the facility is on screen, and once more just before a zoom-out. New hardware, opened bays and automation show up there without extra code. Code that finds bays must search inside `#bays`, never the whole document, or it may hit a camera copy.
- **Navigation:** every screen is a frame with its way back *inside* it, top-left: rooms have "← Facility" in a `.room-bar` (inside `.room-frame`, or inside `#hub` for the server room), and a bay has "← Rack" in its `.module-bar`. The server room's bar lives in the hub, so it hides with the hub when a bay opens.
- **Training Cluster screen:** just the trail, the push button and the strength meter with the push cost. No help essays or tips on screen.
- **No noise:** routine events (new upgrades available, saves, runs) go to the Journal's log only. Nothing on the room screens echoes the log.
- **Escape** zooms out one level: bay → server room → facility. `exitBay` clears `openBay` at once, so a second Escape during the animation still works.
- **Lab:** the Workbench (actions), the automation budget (once you own automation), and one **station** per upgrade group (`STATIONS` over `E.TABS`):
  - Server cabinets: the hardware you own, racked (`renderCabinets`). Every `per` levels of a hardware upgrade adds a `size`-U unit in that hardware's style (`HARDWARE_UNITS`). Units stack from the bottom, a new cabinet starts when one is full (`CABINET_U`), and new units slide in. Camera copies strip the `fresh` class so the animation doesn't replay.
  - Software terminal: a green-screen monitor.
  - Research wall (Algorithms) and Isolation chamber (Consciousness).
  - The next locked station shows as an unnamed "Sealed station"; later ones are hidden.
  - Fully owned upgrades hide.
- **Server room:** one tall rack (`.rack`). Decorative rack units (switch, power supplies, cable tray, blanking plate) sit between the bays, and each bay has its own hardware art (`BAY_ART` counts, styled per `data-bay`): GPU blades, a disk array, a patch panel, a reactor core. Locked bays: the next one is a sealed shutter (`???`), the rest are blanking plates. Clicking a bay zooms into it (`enterBay`/`exitBay`). Only the Training Cluster is built. A new module is a `.module[data-module=id]` block in `#moduleView` plus `built: true` in `BAYS`.
- **R&D:** long-term projects. Project: Transcend (prestige) plus sealed project slots for the planned prestige rework. Opens once a Transcend is possible or has happened.
- **Journal** (`<dialog>`): full log, milestones and achievements, stats, settings.
- Modules run only while zoomed in (`openBay`).
- **Screen sizes:**
  - Phone (≤ 640 px) and tablet / small laptop (≤ 960 px) reflow the layout.
  - Desktop is the base; from 1600 px the content widens to 1480 px.
  - Large screens scale the whole UI with CSS `zoom` through `--ui-scale`: 1.25 from 2200 px (1440p), 1.6 from 3000 px, 1.9 from 3600 px (4K at 100%).
  - Under zoom, `getBoundingClientRect` returns screen pixels but transforms use page pixels, so `zoomFrames`/`roomZoom` divide offsets by `uiScale()` and the canvas multiplies its backing-store resolution by it. Full-height rules use `calc(100dvh / var(--ui-scale) - …)`.
  - Check new UI at 390, 1280, 2560 and 3840 px.

## Verifying changes

1. `node --test` must pass; add tests for new rules.
2. For balance changes, simulate a run in Node with the engine and `training-path.js`: a bot that launches rolls, pushes when the ball stalls on an upslope, and spends XP on Training upgrades. Current first-run results with a bot that lands a clean sprint half the time (and passes `friction`/`hillScale` to `createRoll`): first skill ≈ 6 min, General AI ≈ 37 min, Superintelligence ≈ 1 h 30 min (the bot clicks three times a second throughout, so real players are slower). The gaps between skills should keep growing.
3. Load the page (Playwright/Chromium works in cloud sessions) and check the console for errors at ~390, 1280, 2560 and 3840 px widths.

## Conventions

4-space indent, semicolons, single quotes, `camelCase`. Player-facing messages go through `log(message, type)` (`info | success | warning | special`) and `toast()` in `game.js`. No frameworks, bundlers or CDN libraries unless asked.
